--- What happens when you hit /projects/ ---

Chain:

GET /projects/
      │
      ▼
ProjectListView.as_view()     ← LoginRequiredMixin checks first
      │
      ├── not logged in → redirect to /login/?next=/projects/
      │
      └── logged in
            │
            ▼
      ListView.get()           ← inherited, not overridden
            │
            ▼
      ProjectListView.get_queryset()  ← overridden
            │
            ├── user.role == MANAGER
            │       └── Project.objects.filter(archived=False).order_by("name")
            │              returns ALL non-archived projects
            │
            └── user.role == MEMBER
                    └── ProjectMembership.objects.filter(user=user)
                               .values_list("project_id", flat=True)
                               → [2, 5, 9]  (just the IDs)
                        Project.objects.filter(archived=False, id__in=[2,5,9])
                               returns only their projects
            │
            ▼
      ListView puts queryset into context as "projects"
      (context_object_name = "projects")
            │
            ▼
      render_to_response()
            │
            ▼
      renders "tracker/project_list.html"
      with {{ projects }} available in the template

Verbal explanation:

When you hit /projects/, Django matches the URL to ProjectListView. Before anything
else, LoginRequiredMixin runs — it checks if the user is logged in. If not, it
redirects straight to /login/?next=/projects/. If yes, it lets the request through.

Django then calls ListView.get() (inherited — we didn't override it). ListView's job
is to fetch a list of objects and render a template. It calls get_queryset() to get
that list — and this is where our code runs.

Inside get_queryset(), we check the user's role. If they're a manager, they get all
non-archived projects. If they're a member, we first query ProjectMembership to find
which project IDs they belong to, then filter Project to only return those — so
members only ever see their own projects.

ListView then takes that queryset and puts it into the template context under the name
"projects" (because we set context_object_name = "projects").

Finally, render_to_response() kicks in (inherited from TemplateResponseMixin), picks
up "tracker/project_list.html", combines it with the context, and sends the rendered
HTML back to the browser. The template can now loop over {{ projects }} to display
the list.

--- What happens when you hit /projects/<pk>/ ---

GET /projects/<pk>/
      │
      ▼
ProjectDetailView.as_view()
      │
      ▼
LoginRequiredMixin checks first
      │
      ├── not logged in → redirect to /login/?next=/projects/<pk>/
      │
      └── logged in
            │
            ▼
      DetailView.get()          ← inherited
            │
            ▼
      get_object()              ← inherited (model = Project)
            │  SELECT * FROM tracker_project WHERE id = <pk>
            │  → returns Project instance OR 404 if not found
            │
            ▼
      ProjectDetailView.get_context_data()  ← overridden
            │
            │  member_ids = project.memberships.values_list("user_id", flat=True)
            │  → [3, 5, 7]  (IDs of users in this project)
            │
            │  non_members = User.objects.exclude(pk__in=member_ids)
            │  → all users NOT already in the project (for the add-member dropdown)
            │
            │  ctx = {
            │      "project": project,       ← the Project object
            │      "non_members": <queryset> ← for the add-member form
            │  }
            │
            ▼
      render_to_response(ctx)
            │
            ▼
      renders "tracker/project_detail.html"
      with {{ project }}, {{ project.tasks.all }},
      {{ project.memberships.all }}, {{ non_members }}
      all available in the template

Verbal explanation:

A GET to /projects/<pk>/ first checks login via LoginRequiredMixin. Then
DetailView.get() runs and calls get_object() — since we set model = Project, Django
automatically does Project.objects.get(pk=pk). If no project with that ID exists,
it raises a 404.

Once it has the project, it calls our overridden get_context_data(). This is where we
add extra data beyond the project itself — specifically non_members: all users who are
NOT already in this project, used to populate the "Add Member" dropdown in the
template. We compute it by first getting current member IDs from project.memberships,
then excluding those from User.objects.all().

The context is then passed to render_to_response() which renders project_detail.html.
In the template, {{ project.tasks.all }} and {{ project.memberships.all }} are
available as reverse relations directly on the project object — Django resolves those
as additional queries when the template accesses them.

--- What happens when you hit /projects/new/ ---

GET /projects/new/
      │
      ▼
ProjectCreateView.as_view()
      │
      ▼
@manager_required decorator runs first
      │
      ├── not logged in → redirect to /login/
      ├── logged in but role == MEMBER → raises PermissionDenied (403)
      │
      └── logged in and role == MANAGER
            │
            ▼
      CreateView.get()          ← inherited
            │
            ▼
      get_form()                ← inherited
            │  instantiates ProjectForm() with no data (empty form)
            │
            ▼
      render_to_response()
            │
            ▼
      renders "tracker/project_form.html"
      with empty {{ form }} in the template


POST /projects/new/   (form submitted)
      │
      ▼
@manager_required runs again
      │
      ▼
CreateView.post()             ← inherited
      │
      ▼
get_form()                    ← inherited
      │  instantiates ProjectForm(data=request.POST)  ← bound with submitted data
      │
      ▼
form.is_valid()
      │
      ├── INVALID → render_to_response() with form errors shown
      │
      └── VALID
            │
            ▼
      ProjectCreateView.form_valid(form)  ← overridden
            │  form.instance.owner = request.user  ← sets owner before saving
            │
            ▼
      super().form_valid(form)   ← CreateView saves the object to DB
            │  calls form.save() → INSERT INTO tracker_project ...
            │
            ▼
      get_success_url()          ← overridden
            │  returns /projects/<new_pk>/
            │
            ▼
      redirect to project detail page

reverse_lazy("project_detail", kwargs={"pk": self.object.pk}) builds the URL /projects/<pk>/ from the URL name instead of hardcoding the path.
Three things happening here:
reverse_lazy — same as reverse() but evaluated lazily (only when actually needed). 
Used in class-based views because the URL conf might not be fully loaded when the class is defined. 
In function-based views you'd use reverse() instead.

Verbal explanation:

A GET to /projects/new/ first hits the @manager_required decorator — members get a
403, unauthenticated users get redirected to login. If the user is a manager,
CreateView.get() runs, creates an empty ProjectForm, and renders project_form.html
with a blank form.

When the manager fills in the form and submits (POST), the same decorator check runs
again. CreateView.post() binds the submitted data to a new ProjectForm and calls
is_valid(). If validation fails (e.g. key is missing), the form re-renders with error
messages.

If valid, our overridden form_valid() runs — this is where we set
form.instance.owner = request.user before saving, because the owner field isn't in
the form (the user shouldn't pick it themselves). Then super().form_valid() calls
form.save(), which does the actual INSERT into the database, and get_success_url()
redirects to the newly created project's detail page.

    │
    ▼
EmailLoginView.as_view()
    │
    ▼
LoginView.post()          ← inherited, not overridden
    │
    ▼
EmailLoginView.get_form() ← overridden
    │  • calls get_form_kwargs() → pulls POST data
    │  • pops "request" (EmailLoginForm doesn't expect it)
    │  • returns EmailLoginForm(data=POST_data)
    │
    ▼
form.is_valid()           ← Django runs field validation
    │
    ├── INVALID → re-render login page with errors
    │
    └── VALID
          │
          ▼
    EmailLoginView.form_valid() ← overridden
          │
          ▼
    form.get_credentials()
          │  returns {"username": email, "password": password}
          │
          ▼
    authenticate(request, **credentials)
          │
          ├── None → form.add_error("Invalid email or password.")
          │              └── form_invalid() → re-render login page
          │
          └── User object
                │
                ▼
          login(request, user)   ← sets session cookie
                │
                ▼
          super(LoginView, self).form_valid(form) -->  FormView.form_valid() --> return HttpResponseRedirect(self.get_success_url()) -->  get_success_url() returns LOGIN_REDIRECT_URL → /projects/.
                │
                ▼
          redirect to LOGIN_REDIRECT_URL → /projects/
